# 02. 개발 규칙

## 진입 순서와 역할

[AGENTS.md](../AGENTS.md), [.codex/pave/config.md](../.codex/pave/config.md), [코드 안내](07-codebase-guide.md)를 따른다. 제품 결정은 Notion, 디자인 결정은 Penpot에 반영한다. 사용자가 설계·최종 검수를 맡고 에이전트가 구현한다.

이 문서는 개발·코드 스타일·Git·협업·에셋 관리의 기준 문서다. 아래 작업 규칙과 코드 스타일은 2026-10-20 사용자 확정 사항이다. 폴더별 책임·파일 배치·모듈 연결은 [아키텍처](06-architecture.md)를 따른다. 기획 원문은 Notion, 편집 가능한 디자인 원본은 Penpot을 계속 따른다.

## 저장소에서 확인한 사실

- Godot 4.7 선언, GDScript·`.tscn`·`.tres` 사용. 게임용 패키지 매니저·Node 빌드 시스템은 없다.
- 기존 GDScript에는 들여쓰기 방식이 혼용되어 있다. 현재 파일의 관례를 프로젝트 표준으로 간주하지 않고 아래 확정 스타일을 적용한다.
- `tools/build_scenes.py`는 이전 시안의 검토용 생성 도구다. `.godot/scene_previews/`에만 출력하며 현재 앱의 초기화·설치·빌드 단계로 실행하지 않는다.
- 런타임 음료 카탈로그는 `src/data/drink_catalog.gd`다. 미리보기 생성 도구도 `tools/export_catalog.gd`를 통해 같은 정의를 읽으며 별도 JSON 원본을 두지 않는다.

## 변경·협업

- 작은 범위로 수정하고 현재 소유 모듈과 공유 리소스를 재사용한다. 목적에 없는 인접 정리·재설계를 하지 않는다.
- 기획 확정·구현 현황·제안 수치를 구분한다. 원본에 반영되지 않은 변경은 미동기화로 기록한다.
- 새 작업은 작업별 `codex/<task-name>` 브랜치를 사용한다. 작업명은 내용을 알 수 있는 영어 소문자와 하이픈으로 쓴다. 예: `codex/drink-unlock`.
- 기능·문서 등 자연스럽게 함께 리뷰할 작업 단위를 구현하고 필요한 검증을 마치면 별도 요청 없이 로컬 커밋한다. 실패하거나 미완료인 검증은 통과로 기록하지 않는다. 다른 작업자의 변경은 해당 커밋에 섞지 않는다.
- 커밋 접두어는 영어(`feat:`, `fix:`, `docs:`, `chore:`, `test:`, `refactor:`), 내용은 구체적인 한국어로 쓴다. 기능 관련 문서는 같은 커밋에 포함한다.
- 작업은 필요한 검증과 코드 품질 검사를 통과한 뒤 반드시 로컬 `main`에 머지한다. 작업 요청에는 해당 작업의 로컬 머지까지 포함되며 매번 별도 승인을 요구하지 않는다. 머지 후 `main`에 작업 커밋이 포함되었는지 확인하고 통합 결과에 필요한 검증을 수행한다. 검증 실패·미해결 충돌·다른 작업의 변경 혼입이 있으면 먼저 해결하고, 해결하지 못한 작업은 완료로 보고하지 않는다.
- push·PR 생성은 사용자가 요청했을 때만 진행한다. 로컬 `main` 머지를 원격 반영·릴리스 승인으로 확대하지 않는다.
- 동시에 작업할 때는 파일별 담당 범위를 먼저 정한다. 같은 파일을 수정하기 전 최신 변경을 다시 확인하고, 다른 작업자의 수정은 보존한다. 공유 체크아웃의 브랜치 전환은 진행 중인 다른 작업과 조율한다.
- 검증 명령·한계는 [05](05-quality-rules.md)에 모은다. 코드 경계가 바뀌면 [07](07-codebase-guide.md)의 관련 항목만 갱신한다.

## 코드 품질 필수 검사

아래 검사는 에이전트가 매 작업에 수행한다. 사용자가 재사용·중복·파일 배치를 매번 지적해야 하는 방식으로 운영하지 않는다. 해당하지 않는 항목은 이유를 남기며, 증거 없이 준수했다고 표시하지 않는다.

### 작성 전: 기존 구현과 변경 위치 확인

- [코드 안내](07-codebase-guide.md)의 관련 소유 모듈과 직접 호출 관계를 확인하고, 같은 기능·규칙·UI가 이미 있는지 이름과 역할로 검색한다. 재사용 가능한 동작을 작성하기 전 `owner-found`(기존 소유자 재사용), `owner-absent`(검색 후 없음), `owner-rejected`(기존 소유자 사용 불가)를 구분하고 경로·검색 근거를 계획 또는 작업 설명에 기록한다.
- UI 작업은 [디자인 규칙](04-design-rules.md)에 따라 채택된 Penpot 원본과 런타임 테마·공유 컴포넌트를 확인한다. 사용할 원본·테마·컴포넌트 경로를 먼저 밝힌다. 기존 값이 있는 색·폰트·간격·버튼 스타일·상태를 화면마다 하드코딩하거나 복제하지 않는다. 필요한 확장은 공유 소유자에 반영하며 디자인 시스템 변경·이탈은 사용자 결정으로 다룬다.
- 새 파일마다 경로·단일 책임·사용할 호출자·기존 파일을 확장할 수 없는 이유를 변경 계획에 명시한다. 정상적인 파일 배치는 에이전트가 기존 경계 안에서 결정한다. 이유 없이 루트 파일·범용 `utils`/`helpers`·두 번째 테마/카탈로그/저장소를 만들지 않는다. 씬·스크립트·리소스의 정당한 분리는 허용하며, 파일 수를 줄이려고 기존 파일에 무관한 책임을 몰아넣지 않는다.

### 작성 중: 하나의 규칙은 하나의 소유자에서 관리

- 같은 가격·보상·저장·금액 표기·해금 규칙은 기존 함수를 호출하거나 해당 소유자를 확장한다. 화면별 복사본이나 별도 상태 원장을 만들지 않는다. 필요한 입력·상태 차이는 기존 컴포넌트·리소스의 계약 안에서 표현한다.
- 기존 구현을 쓰기 어렵다는 이유로 조용히 우회 구현을 추가하지 않는다. `owner-rejected`는 중복 소유권이 생기는 설계 결정으로 드러내고 사용자와 해소한다. 단순히 코드 모양이 비슷하다는 이유만으로 서로 다른 도메인을 공통화하지 않으며, 사용처가 없는 범용 기반 클래스·플러그인 구조를 미리 만들지 않는다.
- 표현·입력은 기존 진행 소유자에게 요청하고 결과를 표시한다. UI가 별도로 재화를 차감·저장하거나, 카탈로그가 게임/UI를 역참조하는 등 현재 의존성 경계를 깨지 않는다. 경계 변경이 필요하면 구현 전에 설계에 포함한다.
- 오류를 숨기는 성공값·빈 예외 처리·검증 생략으로 작업을 통과시키지 않는다. 변경으로 생긴 미사용 코드·임시 파일·디버그 출력은 제거하고, 생성 씬·테마를 덮어쓰는 도구는 의도된 범위에서만 사용한다.

### 완료 전: 실제 diff를 검토

- 새 파일·추가 함수·상수·테마 override를 실제 diff에서 검토한다. 각 추가가 요청 범위와 기존 소유권에 맞는지, 같은 동작·디자인 값이 이미 있는지 다시 확인한다. 위반은 머지 전에 수정한다.
- 공유 코드·리소스 변경은 직접 사용하는 화면과 호출자의 영향을 확인한다. 중요한 동작·저장 경계는 관련 회귀 검증, UI는 필요한 상태와 실제 화면 검수를 수행한다. 테스트를 통과시키기 위한 기대값 완화로 결함을 숨기지 않는다.
- 완료 보고에는 재사용한 소유자·컴포넌트, 새 파일의 이유(없으면 없음), 실행한 검증·미검증 항목, `main` 반영 커밋을 간단히 남긴다. 매번 별도 검수 문서를 만들 필요는 없다.

문서 규칙은 에이전트의 필수 실행·검토 기준이다. 현재 린터·CI가 이 검사를 자동 강제하는 상태는 아니며, 의미상 중복·디자인 일치·책임 분리는 코드와 화면 검토가 필요하다. 자동 검사 도입 여부와 도구 선택은 별도 설정 작업으로 다룬다.

## 코드 스타일

새 코드와 수정하는 부분부터 적용한다. 관련 없는 기존 코드의 일괄 포맷·이름 변경은 별도 작업으로 다룬다.

| 항목 | 확정 규칙 |
| --- | --- |
| GDScript 들여쓰기 | 탭, 표시 폭 4칸 |
| 텍스트 파일 | UTF-8, LF, 파일 끝 개행, 줄 끝 공백 제거 |
| 스크립트·씬·리소스 파일명 | `snake_case`: `drink_catalog.gd`, `purchase_button.tscn` |
| 클래스·노드 이름 | `PascalCase`: `DrinkCatalog`, `PurchaseButton` |
| 함수·변수 이름 | `snake_case`: `purchase_drink`, `current_gold` |
| 상수 | `UPPER_SNAKE_CASE`: `MAX_DRINK_COUNT` |
| 내부 멤버 | `_` 접두어: `_refresh_ui`, `_current_selection` |
| 타입 | 함수 인자·반환값·멤버 변수에 명시한다. 타입이 명확한 지역 변수는 `:=`를 허용한다. |
| 줄 길이 | GDScript는 100자 이내로 작성한다. |
| 문자열·목록 | 큰따옴표를 기본으로 사용하고, 여러 줄 목록의 마지막 항목에도 쉼표를 붙인다. |
| 언어 | 식별자는 영어, 문서·주석은 한국어. 주석은 코드 반복 설명보다 이유와 제약을 기록한다. |

[.editorconfig](../.editorconfig)는 문자 인코딩·개행·공백과 GDScript 들여쓰기·줄 길이 기준을 선언한다. 편집기의 지원 범위에서 적용되며, 이름·타입·따옴표까지 검사하는 포매터나 린터는 아직 설정되지 않았다. 생성된 씬·리소스에 GDScript의 줄 길이 제한을 적용하지 않는다.

## 에셋 관리와 보관 범위

- 편집 가능한 디자인 원본은 Penpot에서 관리한다. 로컬 `design/`을 Penpot 전체 복제본이나 작업 이력 보관함으로 유지하지 않는다.
- 게임이 실제로 사용하는 이미지·아이콘·스타일 리소스는 저장소의 해당 런타임 경로에서 관리한다. 현재 경로 예시는 `assets/`, `src/shared/ui/`이며, 임의로 중복 복사하거나 전체 경로를 재편하지 않는다.
- 디자인 적용 시 원본 보드·컴포넌트 링크와 적용 파일 경로를 [DESIGN.md](../DESIGN.md)·[design/README.md](../design/README.md)의 해당 안내에서 연결한다. 내보낸 파일은 게임에서 크기·비율·선명도를 확인한다.
- 비교 시안·이전 버전·미리보기·작업 기록은 기본 영구 보관 대상이 아니다. 버전 추적은 Git 이력을 사용하고, 검수용 임시 출력은 필요할 때만 만든다. 현재 작업에 필요한 로컬 소스·산출물이나 사용자가 보관을 요청한 자료만 목적에 맞게 남긴다.
- 이 기준은 앞으로의 보관 정책이다. 기존 자료 삭제나 Penpot 보관함 정리는 별도로 범위를 정하며, 이 문서 추가만으로 기존 파일을 일괄 삭제하지 않는다.
