# Terra 게임 사용자 테스트 지시서·테스트 케이스

작성일: 2026-10-30 KST. 대상: `/Users/hongtaeho/clicker`, 실행 기준 커밋 `a282352`.
요청: Terra가 게임을 직접 실행·조작하여 버그, 시각적 개선점, 애니메이션 보강점을 검수한다.
이 문서는 검수 지시서이며 제품 기획이나 디자인 SSOT를 대체하지 않는다.
실행 결과와 미검증 범위는 [Terra 직접 사용자 테스트 결과](terra-user-test-report.md)에서 확인한다.

## 검수자에게 전달하는 작업 계약

- 역할: QA와 플레이 감각 검수. 직접 실행한 화면과 입력을 근거로 판단한다.
- 허용: 읽기, 실행, 테스트 전용 저장 데이터 준비, 기존 회귀 실행, 화면 증거와 결과 문서 작성.
- 소유 범위: 테스트 실행 환경·증거 및 `docs/terra-user-test-report.md` 작성. 메인 에이전트는 지시서·통합 확인을 담당한다.
- 게임 소스·씬·에셋·자동 테스트·원본 Penpot·Notion은 수정하지 않는다. 발견한 문제를 고쳐서 재현 증거를 없애지 않는다.
- 사용자 기존 진행·설정과 실행 중인 다른 작업을 보존한다. 독립 데이터 경로가 확인되기 전 새 게임·이어하기·설정 저장을 실행하지 않는다.
- 새 테스트 코드는 추가하지 않는다. 기존 회귀는 실제 구매·저장·입력 계약의 보조 증거로만 쓴다. 자동 통과를 직접 플레이 통과로 바꾸지 않는다.
- 실행 또는 GUI 접근이 막히면 실제 오류, 시도한 대안, 여전히 가능한 검증을 기록한다. 보지 못한 애니메이션을 본 것처럼 평가하지 않는다.
- 검수는 완료 범위와 미실행 범위를 모두 반환한다. 최종 제품 합격·출시 판단은 메인 에이전트와 사용자에게 남긴다.

## 관찰 순서와 판정

첫 실행·자연 플레이 → 구매/해금 → 퀘스트·시설 → 피버·중첩 → 저장/재실행 → 창 크기·모션 감소 순서로 진행한다.
관찰은 두 번으로 제한한다. 1차에 묶어서 검수하고, 2차는 결함 재현·모호한 결과 확인에만 사용한다. 수정·무한 폴리싱은 하지 않는다.

각 TC 결과는 `PASS / FAIL / BLOCKED / NOT RUN / OBSERVED` 중 하나다. `OBSERVED`는 주관적 감각·미정 기획의 사실 기록이다.
결함은 가능하면 같은 조건으로 2회 재현하고 횟수(예: 2/2)를 기록한다. 랜덤 결과 미발생은 실패가 아니라 미실행이다.
확률을 소수 표본으로 증명하지 않는다. 가격·차감·단일 지급·입력 차단·저장 복원은 전후 숫자로 확인한다.

발견 사항의 심각도는 실제 영향과 우회 가능성으로 정한다. P0 진행 손실·실행 불가·반복 중복 지급 / P1 주요 흐름 차단·중대한 재화/저장 오류 / P2 우회 가능한 기획 불일치·조작 혼란·시각 가림 / P3 경미한 가독성 마감·선택적 연출 개선.
아래 TC 표의 우선은 실행 순서의 중요도이며, 발견 사항의 심각도와 별개다. Sol 재검토에서 확인한 현상의 영향에 맞춰 이 구분을 명확히 했다.
분류는 `기능 버그 / 기획 불일치 / UX·시각 / 애니메이션 제안 / 환경 제한`으로 분리한다. 제안을 확정 버그처럼 작성하지 않는다.

## 시각·애니메이션 집중 체크

정지 사진만으로 움직임 합격을 판단하지 않는다. 각 사건의 시작/중간/끝을 직접 관찰하고 가능하면 짧은 영상 또는 시점이 적힌 연속 캡처를 남긴다.

| ID | 검수 대상 | 구체적 질문·기준 |

## 회귀 검사와 결과 인수 조건

기존 명령은 `docs/05-quality-rules.md`를 따른다. import/parse 및 관련 회귀를 독립 프로세스로 실행하고 완료 문구·종료 코드·`SCRIPT ERROR`를 함께 확인한다. 이전 실행 기록을 이번 통과 근거로 사용하지 않는다.
수동 재현과 자동 회귀가 서로 다르면 둘 다 유지하고 차이를 설명한다. 기존 테스트가 통과하는 기획 불일치도 있을 수 있다.

결과 문서에 다음을 포함한다.

1. 테스트 대상 커밋·환경·실제 GUI 접근 여부·독립 저장 경로·검수자/모델.
2. TC-01~28, VA-01~10 **전 행**의 판정·실제 절차/초기 상태·전후 수치·증거·미실행 이유.
3. 결함별 ID/분류/우선순위/기대/실제/최소 재현/재현 빈도/증거/사용자 영향/확인된 소유 경로. 원인 추정은 추정으로 표시.
4. 잘된 점 2~3개와 개선 제안 최대 5개. 관찰과 개인 취향을 구분한다.
5. 실행한 명령·완료 출력·오류·차단 및 미실행 범위. Windows/릴리스/전체 언어를 검증했다고 주장하지 않는다.
6. 원본 저장 불변·프로세스 종료·임시 환경 정리·변경 파일 목록.

완료 기준은 모든 케이스의 통과가 아니라, 실행 가능한 범위를 실제로 조작하고 모든 케이스의 증거 또는 구체적인 미실행 이유가 남으며, 결함과 제안을 다음 작업자가 재현할 수 있는 상태다.
